# MySQL 全库性能审计与优化实施记录

日期：2026-07-15

## 结论

- MySQL 9.5.0，物理内存 16GB，数据目录约 205GB；`chenyiyun` 约 3.3GB，`tushare_stock` 约 199GB。
- buffer-pool 命中率约 99.81%，磁盘临时表比例约 0.006%，当前不支持立即扩大 buffer pool。
- `Innodb_log_waits=0`，但 7 月 10、13、14 日峰值 ETL 期间出现 redo checkpoint 落后告警。保留 1GB 配置，先观察完整夜间周期；再次告警时单独升至 2GB。
- Performance Schema 显示 `app_notification_channel` 的 schema 默认值 upsert 已执行约 258 万次、累计约 1,440 秒。Web schema 迁移已移到生产启动阶段，请求期兼容调用在初始化后直接返回。
- `score_rank_daily` 约 430 万行/2.64GB，但最新交易日仅约 5,166 行；现有 `(trade_date, symbol)` 索引可将候选页限制在单日范围，未增加高写放大的多列排序索引。

## 已执行变更

### B/S 索引

在线创建为 invisible、验证后转 visible：

| 索引 | 验证查询 | 优化前 | invisible 验证 | 发布后 | 结论 |
|---|---|---:|---:|---:|---|
| `idx_bs_batch_stock(batch_date, stock_code)` | 最新日信号列表 | 228ms | 2.36ms | 2.61ms | 约 98.9% 改善 |
| `idx_bs_stock_state(stock_code, batch_date, has_buy_signal, has_sell_signal)` | 每股最新 B/S 状态 | 90ms | 51.1ms | 52.9ms | 约 41% 改善 |

索引均通过 `ALGORITHM=INPLACE, LOCK=NONE` 发布。回滚必须先执行 `hide`，观察一个业务周期后才能 `drop`：

```bash
set -a; . ~/.config/chenyiyun/web.env; set +a
.venv/bin/python scripts/maintenance/manage_mysql_indexes.py hide bs_batch_stock --confirm hide:bs_batch_stock
.venv/bin/python scripts/maintenance/manage_mysql_indexes.py drop bs_batch_stock --confirm drop:bs_batch_stock
```

### Web 查询

- 三个评分页改为明确字段列表，不再从宽表读取全部列。
- B 点候选页改为数据库端 `COUNT + ORDER BY + LIMIT/OFFSET`，仅对当前页执行增强计算。
- 排序字段继续使用白名单，保留原有 URL/API 参数。
- 部署后本机 10 次采样：候选页 P50/P95 为 53/92ms，全量页为 42/45ms，自选页为 49/50ms。

### 运维工具

- `audit_mysql_performance.py`：只读采集表、索引、状态、锁、I/O、digest 和候选执行计划。
- `manage_mysql_indexes.py`：索引 stage/promote/hide/drop，所有变更都需要显式确认。
- `tune_mysql_runtime.py`：一次只允许修改一个受控参数，并输出回滚命令。
- `migrate_web_schema.py`：在启动/维护阶段执行 Web schema 迁移。
- `reconcile_mysql_service.sh`、`rotate_mysql_error_log.sh`：治理重复服务和错误日志。

完整基线及验证证据位于 `exports/db_performance/`。

30 日批任务基线中，平均耗时最高的是 `sina_picture` 1,650 秒、`sina_analyse` 611 秒、`candle_diag_scan` 330 秒、`trusted_strategy_backtest` 315 秒和 `sina_score` 302 秒；后续夜间周期按这些任务逐项比较。

## P0 尚需 root 执行

当前健康实例是 6 月 30 日手工启动的 `_mysql` 进程；系统 LaunchDaemon 同时反复尝试启动第二实例，`runs` 已超过 46,000 次，`/Users/Shared/mysql_external.err` 已约 978MB。当前自动化会话没有 sudo 权限，未强杀任何数据库进程。

先停止失败启动器并保留健康实例：

```bash
sudo scripts/maintenance/reconcile_mysql_service.sh --execute
sudo scripts/maintenance/rotate_mysql_error_log.sh
```

执行后要求：数据目录只能有一个 `mysqld` 所有者，错误日志不再增长。后续维护窗口再将手工实例平滑迁移到唯一的系统 LaunchDaemon；不要直接 kill 正在服务的 PID。

维护窗口内完成健康实例的正常关闭后，安装带单实例门禁的 LaunchDaemon：

```bash
sudo cp scripts/maintenance/com.chenyiyun.mysql.plist /Library/LaunchDaemons/
sudo chown root:wheel /Library/LaunchDaemons/com.chenyiyun.mysql.plist
sudo chmod 644 /Library/LaunchDaemons/com.chenyiyun.mysql.plist
sudo launchctl bootstrap system /Library/LaunchDaemons/com.chenyiyun.mysql.plist
```

## 大表与配置决策

| 表 | 大小 | 决策 |
|---|---:|---|
| `ods_stk_factor` | 31.3GB | 保留；先确认日期范围和主键，再评估月分区 |
| `ods_plate_raw` | 19.1GB | 优先制定原始载荷保留期；索引已占约 5.3GB |
| `ads_strategy_feature_snapshot_di` | 14.4GB | 调查单行 payload；优先冷热归档而非直接分区 |
| `ads_strategy_stock_debug_di` | 13.4GB | 优先缩短 debug 数据保留期 |
| `score_rank_daily` | 2.64GB | 暂不拆表；先上线显式列和分页，观察一个周期 |

参数发布门禁：

1. 再次出现 redo checkpoint 告警时，将 `innodb_redo_log_capacity` 从 1GB 单独升到 2GB。
2. 仅当 buffer-pool 命中率持续低于 99%或 `Innodb_buffer_pool_wait_free` 在采样窗口继续增长时，才从 4GB 升至 6GB。
3. `innodb_io_capacity` 必须在外置 SSD 随机写/刷盘基准完成后调整，不使用经验值直接覆盖。
4. 每次只改变一个变量，观察至少一个完整夜间批处理周期，并保留工具输出的回滚命令。

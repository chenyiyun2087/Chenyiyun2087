## 修复方案

1. 封包和正式证据复用 `release_runtime.RUNTIME_STATUS_EXCLUDES`，与生产运行预检使用同一清单。生成目录及其符号链接不误算为源码改动；新增源码、修改源码或配置、发布 SHA 不符仍阻断。输入数据、快照哈希、PIT 和不可变封包门禁保持独立。
2. 回归构造真实 Git 仓库：提交旧生成数据，再改为两个 canonical 目录链接，写入新日数据，验证两个入口均可通过；随后修改源码、配置、增加未跟踪代码或错配 SHA，验证仍阻断。
3. 保留 origin/main 现行 PAUSED 稳定性设置，发布仅使用已有 --stability-hotfix 例外，不把旧分支的解除暂停状态带回远端。合入 origin/main 上既有 AlertHub 改动，保留线上已验证的租约、启动监督、证据共享、断线恢复、新浪弹窗及局部失败重试等修复；在隔离工作区解决冲突并测试，保留主工作区用户 WIP。
4. 从洁净提交发布稳定性修复。在真实封包入口完成验证后，按 28 日封包→卖出预提交→净值、29 日早间预提交的顺序恢复，并核对文件合同、时间戳及全账本守恒。迟到恢复单独记录，不倒签为 28 日按时完成；不提升正式历史 PIT 或 E4 资格。
5. 数据中心继续按已提交的方案等待真实 THS 补齐：新鲜重采明确业务日，原覆盖及关键字段门槛通过后续跑源和独立完整性任务。禁止填零、用其他资金流替代、移除真实缺失证券或改写 22:30 INCOMPLETE。
6. 测试和在线复核通过后推送 origin/main，使用 `git ls-remote` 核验远端 SHA。不强推，不提交其他任务报告或生成数据。

## 结论

v4.7 完成了真实数据进入长周期 PIT builder 的最后一公里接口，并冻结了无真实
数据条件下的 Alpha 算法迭代。当前工作区没有 adapter config、只读数据库连接

## 数据适配层

新增 `scripts/research/pit_data_adapter.py`：

- `FILE`：读取 CSV/Parquet 冻结快照；
- `MYSQL`：只接受只读 `SELECT`，从 `CHENYIYUN_DB_URL` 读取并冻结 Parquet；
- 五类统一输入：
  - market
  - universe
  - financial
  - industry
  - adjustment
- 每类记录 content SHA、schema hash、source version 和 provider；
- 全局记录 release、evidence origin、带时区 retrieved_at、schema semantic
  version 和 field definition hash。

缺配置、连接、文件、列、版本或 schema 不一致均失败关闭。

## PIT 合同增强

长周期 builder 现在要求独立 financial snapshot，并新增：

- 财务：
  - `financial_period_end`
  - `announcement_date`
  - `financial_available_at`
  - `revision_id`
  - `financial_source_snapshot_sha`
- 公司行动：
  - `corporate_action_type`
  - `ex_date`
  - `record_date`
  - `adjustment_factor_version`
- 证券生命周期：
  - `security_status_transition`
- 数据语义：
  - `schema_semantic_version`
  - `field_definition_hash`

五类数据继续要求无重复键、每日覆盖≥95%、可用时间不晚于 T 日15:30、预热后
不少于252日。

## 2026-07-31 内部升级尝试与审阅结论

2026-07-31 进行了内部升级尝试，创建了 MySQL adapter config，运行了 PIT
builder，并生成了声称 E3 级别的因子面板和验证报告。

### 独立审阅结论（2026-07-31）

**总体结论：REQUEST CHANGES，不接受 E3 认定。评分 4/10。**

发现 6 个 P0 问题和 3 个 P1 问题：

**P0 问题：**
1. 仓库提交了明文 root 数据库凭据
2. Builder 自动回填缺失的 available_at 为 signal_time（绕过 PIT 门禁）
3. Builder 用 0.0 填充缺失 PB，然后基于 notna() 计算覆盖率（财务覆盖率虚高为 100%）
4. `evidence_origin: HISTORICAL_REAL` 仅为配置字符串，无任何独立验证
5. Adapter→Builder 证据链断裂（Adapter PASS 后手工修改 Parquet 和 manifest SHA）
6. Runner 脚本不可按代码原样复现

**P1 问题：**
1. Builder 未执行验收配置中声明的全部门禁（仅检查 ~11/25 项）
2. 文档、代码和证据结论互相冲突
3. 旧版本配置被全部别名到 v4.7（破坏历史可复现性）

**正面评价：**
- 资本防火墙有效（保持 NO_SCALE / 0 元）
- S1/S3 与 E1/E3 分层方向正确
- fail-closed 逻辑基本正确
